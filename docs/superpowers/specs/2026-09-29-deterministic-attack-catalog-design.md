# Детерминированный каталог атак — архитектурная спецификация

**Статус:** утверждено владельцем 2026-09-29; направление — переход к игре без runtime-моделей и к выбору заранее заданной карточки.

## Цель и границы

Заменить свободный текст атаки и весь runtime AI-контур на выбор серверно-доверенной карточки. Сохранить десять стартапов, финансовые паспорта, формулы экономики и score, защиту, leaderboard, один игровой раунд на шаг, визуальное направление и браузерные ассеты.

Одна партия остаётся ограниченной браузерной сессией: случайно выбранный стартап, три раунда по три месяца, максимум девять месяцев, досрочное банкротство и итоговый score 0–1000. Случайный выбор startup остаётся вне экономического расчёта. Повтор одной версии startup, одного начального состояния и одной последовательности choice ID всегда воспроизводит одинаковый ledger, защиты, состояние и результат.

Изменение не добавляет новые финансовые формулы, категории защиты, админ-функции, AI/NLP, runtime внешние вызовы или сторонние зависимости. Статическая генерация изображений в разработке и готовые игровые assets сохраняются.

## Модель карточки и расчёт

Источник истины каталога — `data/attack_choices.json` с общей JSON Schema. Каталог имеет версию и настраиваемый `choices_per_round`; начальная величина — 4, то есть 12 вариантов на startup и 120 на весь каталог. Каждая карточка принадлежит одному startup и одному из трёх раундов.

Карточка содержит уникальный ID, slug startup, номер раунда, заголовок, краткое описание, заголовок результата, вид атаки, severity, scale, feasibility, целевые stream ID, при необходимости weakness ID, weakness match, duration, stack group, допустимые ссылки на startup facts и готовые тексты события. Поля ограничены enum и числами текущего engine. Денежные коэффициенты и произвольные команды движку в карточке не хранятся.

Каталог преобразуется сервером в существующий `ValidatedAttack`. Расчёт остаётся в текущих `engine.calculator`, `engine.defense` и `engine.scoring`: severity/scale/feasibility/weakness match задают шок по текущим формулам; тип атаки задаёт уже существующие incident-cost и reputation правила; effects, decay, stacking, defense projection, bankruptcy и score не получают новых веток на ID карточки. Для критической severity в карточке должны быть валидные доказательные fact IDs согласно действующему engine guard.

Индивидуальные тексты атаки, реакции компании и результата задаются статически в карточках. Сервер возвращает их вместе с результатом, но тексты не влияют на состояние. Числовые вставки допускаются только как шаблоны, заполненные server-side из рассчитанного результата. В первом каталоге все карточки доступны, если совпадают startup и текущий раунд; динамические условия и скрывание карточек не вводятся. Так остаётся как минимум один валидный выбор, а правила требований не требуют новой механики.

## Игровой поток и API

При создании сессии сервер сохраняет в ней версию каталога и snapshot 12 карточек назначенного startup. Публичные поля карточек отдаются вместе с bootstrap/session; закрытый startup profile и внутренние данные не раскрываются. Тело хода содержит только `{"choice_id":"..."}`. Сервер определяет текущий раунд из сессии; клиент не присылает round number или параметры карточки. Существующие CSRF и idempotency headers сохраняются.

Сервер в одной транзакции блокирует сессию, проверяет её владельца и статус, номер раунда, idempotency key, принадлежность карточки startup/версии/раунду и наличие ещё не разрешённого хода. Он получает параметры и narrative из серверного каталога/snapshot, запускает engine синхронно и атомарно сохраняет selected choice, его snapshot, outcome, ledger, состояние и финальные score/status. Повтор того же ключа и payload возвращает прежний результат; тот же ключ с иным payload — конфликт. Клиент не может прислать или переопределить параметры экономики.

Job polling, постановка AI job, worker ожидание/повторы и provider outage состояния удаляются. Существующие сессии продолжают восстанавливаться через cookie; `continue`, итоговый экран и leaderboard остаются серверными. `/admin` и связанные API удаляются, поскольку после исключения AI у них не остаётся утверждённых функций.

## Данные и миграция

Существующую миграцию `0001_initial_schema.py` не переписывать. Добавить следующую Alembic migration: зафиксировать версию/snapshot каталога у сессий; добавить selected choice ID и snapshot к раундам; убрать поля свободного текста, AI анализа и prompt/provider provenance; удалить AI job, credential, provider runtime/usage/key-test и только AI-настройки таблицы. Сохранить startup snapshots, браузерные cookie hashes, nickname, resolved outcomes, месячные ledger, score и leaderboard history.

Для исторических resolved rounds без карточек оставить choice ID/snapshot пустыми и очистить старый сырой текст/AI analysis; сохранённые финансовые результаты не пересчитывать. Незавершённая старая AI-задача не имеет детерминированного выбора: при миграции удалить её job/round и вернуть сессию к последнему сохранённому состоянию `ready`, не списывая ход. Перед upgrade приложение/worker должны быть остановлены; миграция, fresh install и upgrade покрываются тестами. `0001` остаётся неизменяемой частью истории; upgrade вносится отдельной migration.

## Удаление runtime AI и документация

Удалить provider clients/router/validators/prompts, fake provider, worker/queue, AI-only crypto/auth/config (только если они не нужны оставшемуся runtime), admin AI UI/API, AI package dependencies и AI environment variables. Production compose оставляет PostgreSQL, один API и статический nginx/frontend; никаких worker services и AI secrets. Сохранить существующие библиотеки, используемые другими функциями.

Обновить нормативные документы, API schemas, examples, Docker/runbook, тесты, генераторы/собранный frontend и G0 static checks. Удалить AI-only документы, fixtures и тесты. `MANIFEST.sha256` пересобрать после изменений. Поисковые остатки перечислить с путями и объяснением; runtime-ссылок, отключённых провайдеров и текстов AI-ожидания не оставлять.

## Баланс, приёмка и производительность

Каталог валидируется по schema и связям с startup/stream/weakness/fact IDs; проверяются уникальность choice IDs и количество карточек для всех 30 пар startup/round. Обеспечить минимум один вариант на каждом достижимом ходе.

Для каждого startup перебрать все достижимые последовательности выбора до трёх раундов; после банкротства ветвь терминальна. Создать `BALANCE_REPORT.md` со score min/max/mean/median, bankruptcy rate, числом путей и лучшим/худшим диагностическими путями. Сравнить десять компаний по текущему порогу scoring contract; формулы и базовые финансы не менять. При существенном перекосе показать конкретные цифры и предложенные изменения параметров карточек, не применять их молча.

Тесты покрывают текущие 30 economy golden oracle, engine edge cases, каждую карточку, 100-кратное воспроизведение одинаковых путей, известные golden paths, cross-startup/round spoofing, параметры сверх schema, двойную отправку, idempotency, refresh/resume, миграции, leaderboard и отсутствие runtime AI конфигурации. Выполнить production frontend build без AI credentials и ограниченный benchmark вычисления одного хода; latency сообщать только по фактическому замеру. Целевой production-host RSS/CPU остаётся неизвестным и не считается проверенным локальным benchmark.

## Рассмотренные варианты

1. **JSON-каталог + snapshot карточек сессии (рекомендовано).** Один версионированный источник данных, небольшая запись на партию, без таблиц и админки каталога; выбранная карточка дополнительно фиксируется в раунде.
2. **Каталог в PostgreSQL.** Удобен для будущего редактирования и аудита, но требует seed/CRUD/versioning и не нужен при запрете новой админки.

## Известные ограничения

- В копии workspace нет Git metadata; документ нельзя закоммитить и ветку/историю миграций проверить невозможно.
- `MANIFEST.sha256` сейчас не совпадает с деревом; он будет пересобран, но это не заменяет проверку исходного архива.
- Наличие локальных deployment-конфигов не подтверждает, развернута ли эта схема в production. Миграция сохраняет завершённую игровую историю и добавляет безопасный upgrade path; реальную базу без подключения к серверу проверить нельзя.
